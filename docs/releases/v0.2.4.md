## Changes since v0.2.3

- Run history and detail inspection now survive the application permission
  wrapper, including repositories selected through namespace switching. A
  backend without the optional history capability still returns HTTP 501.
  Storage failures and a successful empty history are not reported as the same
  condition. See [session review operations](../session-review.md).
- Task session cards show escaped summary previews and explicit summary states,
  rather than loading transcripts into the task dialog. Preview metadata is
  resolved in one session query and bound to the exact job, not a reused harness
  session ID. Running/archiving jobs take precedence over queued jobs.
- Selecting a valid run opens a separate session dialog, which lazily requests
  run metadata and paginated output. Back or Escape preserves the task's unsent
  comment. Agent history also offers output inspection for taskless scheduled
  runs. Output polling is scoped to the selected namespace and job and stops
  when the session dialog closes.
- Detail lookups can inspect pending, running, and archiving jobs before a final
  durable result exists. Completed results remain preferred over live metadata.
- Newly captured `agent_output` events carry the exact job ID. The new read API,
  `GET /api/agents/{name}/runs/{jobID}/output`, validates the run/agent identity
  and supports an event-ID `after` cursor and `limit` from 1 to 200. Responses
  contain `events`, `has_more`, and `next_after`.

Durable summaries/run history and migration 018 already existed in v0.2.3.
Do not present those earlier features, scheduled runs, or attachments as new in
this release. The fixes above make review usable through the normal dashboard
and add exact-run output attribution.

## Migration 019 and historical output

[019_session_run_output.sql](../../internal/postgres/migrations/019_session_run_output.sql)
adds nullable `events.job_id bigint` and the partial index
`events_job_id_idx` on `(job_id, id) WHERE job_id IS NOT NULL`.
There is deliberately no foreign key, so removal of a mutable job does not by
itself remove its recorded output. Migration 018 remains the existing
`018_agent_session_runs.sql`, not a new renumbering for v0.2.4.

**Historical output is not backfilled.** Existing event rows retain a null job ID.
Task, agent, and reused session IDs cannot establish which run produced those
rows. The output query returns only `agent_output` events explicitly attributed
to the requested job. Older summaries remain reviewable, but an empty output
pane for an older run is expected and does not establish data loss. The UI
explains the absence of correlated historical output. Do not manually infer or
populate attribution from shared session IDs.

The index is created with ordinary `CREATE INDEX`, not `CONCURRENTLY`. Plan a
maintenance window for DDL locks and index work on a large events table. There
is no measured duration guarantee. Migrations are embedded and tracked per
namespace. The new capture path references `job_id`, so migrate every namespace
before allowing new workers to capture output there.

The SQL Down migration drops the index and column, destroying newly recorded
job attribution. It is not a lossless rollback. Keep a tested pre-upgrade backup
and restore plan rather than treating a binary downgrade or Down migration as a
complete recovery procedure.

## Safe operator upgrade

1. Rehearse on a disposable restore of representative v0.2.3 data, never on
   production as a test. Inventory every namespace, the active manifest, current
   binary version, configuration, and service startup commands. See
   [installation updates](../installation.md#updating) and
   [namespace upgrades](../usage.md#namespaces-and-upgrades).
2. Arrange a maintenance window. Stop old workers and prevent supervisors from
   restarting them. Stop application processes that could write during the
   upgrade. Take and verify a consistent PostgreSQL backup, including namespace
   schemas and migration history, and retain the v0.2.3 binary/configuration.
3. Once publication is approved and artifacts exist, obtain the pinned v0.2.4
   archive for the correct OS/architecture and verify its SHA-256 against that
   release's checksums. Do not use an unpinned `latest` download. Stage the new
   binary without starting workers.
4. Using the new binary and the intended operator configuration, explicitly run
   migrations for **each existing namespace**, including the default namespace:

   ```sh
   looster --config /path/to/config.toml --namespace YOUR_NAMESPACE db migrate
   ```

   Replace the placeholders and verify database/namespace selection first.
   Confirm successful application through migration 019 in each namespace's
   migration history. On a lock timeout or any migration failure, leave workers
   stopped, inspect the cause and actual schema/history, and resolve it before
   retrying. Do not bypass locks, edit migration version records, or start mixed
   worker versions to work around a failure.
5. Review the active manifest and restart only v0.2.4 processes after migration
   succeeds everywhere they serve. Verify existing tasks, summaries, namespace
   switching, and a new controlled run's output. Treat old uncorrelated output
   as an expected limitation, not a reason to rewrite historical events.
6. If recovery is required, stop all writers and follow the rehearsed backup
   restore procedure with the matching old binary/configuration. Account for
   post-backup writes that a restore would lose. Do not blindly downgrade against
   a modified database or run destructive Down SQL on live data.

## Release verification checklist

All boxes are pending release gates, not results of this documentation task.
Run verification against the exact target, separately from this docs branch.
Concurrent coordinator test runs are not evidence until their revision,
configuration, and results are recorded.

- [ ] Verify `git rev-parse v0.2.3^{}` and the exact target SHA above, inspect
  `git log v0.2.3..c8416af0f02f9a45c10a65714974022f1270277b`, and confirm the
  release checkout is clean and contains no preparation-branch code changes.
- [ ] Use the toolchain in `go.mod`. Run `go mod verify`,
  `go run ./scripts/licenses -check`, `go vet ./...`, and build the CLI with
  `go build -buildvcs=false -o bin/looster ./cmd/looster`. Check `--help` and
  `licenses`. Record command outputs and target SHA.
- [ ] Run the CI-equivalent `go test -count=1 -timeout=10m ./...` with a disposable
  PostgreSQL database, built CLI, Chromium, and both browser opt-ins configured
  as in [contributing](../contributing.md#ci-and-browser-integration). Also run
  `(cd scripts/lint-audit && go test ./...)`. A default unit pass with skipped
  database/browser tests is not integration acceptance.
- [ ] Exercise fresh installation and a v0.2.3 restore upgraded through 019 in
  default and non-default namespaces. Verify existing tasks, queues, summaries,
  and history survive, null historical attribution remains null, and new output
  is attributed to its exact job. Record backup/restore rehearsal results.
- [ ] Verify permission-wrapped history and output routes after namespace
  switching, pagination, invalid cursors, wrong agent/job combinations, and
  namespace isolation. Distinguish HTTP 501 capability absence, HTTP 500 storage
  failure, and HTTP 200 empty history.
- [ ] In a browser, verify summary previews without eager transcript requests,
  live and completed run detail, scheduled taskless output, reused-session run
  isolation, lazy pagination, Back/Escape with an unsent comment, and no further
  output polling after close. Verify historical-output messaging and safe text
  rendering. Retain screenshots and request evidence.
- [ ] Before any separately authorized publication, confirm the proposed tag
  will point to the exact target SHA, not this document commit. Require passing
  CI at that revision before release builds. No tag or push is authorized here.
- [ ] After authorized publication, verify all six platform archives and their
  checksum entries, embedded assets/migrations, license notices and HCL source
  ZIP, the pinned installer path, and a clean Compose setup according to
  [releasing](../releasing.md#verify-the-published-release).
